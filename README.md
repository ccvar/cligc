# cligc

一个单二进制的轻量内容站：**Go + SQLite + 服务端渲染**，自带一套 REST API
和一个把这套 API 暴露给 AI 客户端的 **MCP server**。

**这是给站长自己用的，不是一个 UGC 平台。** 没有注册入口，账号只能从命令行
建（`cligc user add`）。站上唯一来自陌生人的内容是评论，而它默认必须人工放行。
如果你想要的是"让很多人来注册发文章"，这个项目不合适——它的每一处取舍都
建立在"作者是可信的、读者不是"这个前提上。

**拿去改。** 结构是按"改起来不打架"设计的：样式和脚本分成
`base / site / admin` 三层，公开页和后台互不加载对方的文件，前端整套换掉
不用碰后台一行（有 lint 守着这条边界，越界直接测试失败）。

没有前端框架，没有构建步骤，没有外部服务依赖。整个站——模板、样式、
脚本、数据库 schema——都编译进一个可执行文件。

```
cligc/
├── cmd/cligc/          子命令入口：serve / mcp / user / token
├── internal/
│   ├── i18n/           界面文案目录（零依赖，含最小复数支持）
│   ├── store/          SQLite 层（schema、CRUD、FTS、发布配额、幂等）
│   ├── tokenize/       中文 bigram 分词，FTS5 能检索中文的关键
│   ├── render/         Markdown 渲染 + UGC 外链处理 + 检索高亮
│   ├── web/            服务端渲染页面 + 后台 + 评论 + SEO 端点
│   ├── api/            REST /api/v1 —— 全站唯一的写入口
│   └── mcp/            MCP server（stdio + Streamable HTTP）
├── skill/              AI 技能包（SKILL.md）
└── deploy/             systemd / Caddy / Litestream / MCP 客户端配置
```

外部依赖三个：`modernc.org/sqlite`（纯 Go，无 cgo）、`github.com/yuin/goldmark`、
以及代码高亮用的 `goldmark-highlighting`（带进 chroma）。
密码哈希用标准库的 `crypto/pbkdf2`，路由用标准库的 `net/http`。

## 快速开始

一键安装（拉源码、构建、建管理员账号）：

```bash
curl -fsSL https://raw.githubusercontent.com/ccvar/cligc/main/install.sh | sh
```

管道跑网上下来的脚本前先看一眼，是个好习惯：

```bash
curl -fsSL https://raw.githubusercontent.com/ccvar/cligc/main/install.sh -o install.sh
less install.sh && sh install.sh
```

脚本不接收密码参数、也不生成密码打印出来——命令行参数会进 `ps` 和 shell
历史，打印出来的会留在终端回滚缓冲区里。它调 `cligc user add` 交互式提示，
输入不回显。

手动装也就三行：

```bash
go build -o cligc ./cmd/cligc
./cligc user add -email you@example.com -name 你的名字 -admin
./cligc serve -addr :8866 -base-url http://localhost:8866 -title "我的站"
```

打开 http://localhost:8866/login 登录，后台在 `/admin`。

## 接上 AI 客户端

1. 后台 `/admin/tokens` 创建 token。**不要勾 `posts:publish`**——
   让 AI 写草稿，你来发布。命令行等价写法：

   ```bash
   ./cligc token create -email you@example.com -name claude-code-local \
     -scopes "posts:read,posts:write,media:write" -days 0
   ```

2. 把 `deploy/mcp-client.json` 的内容合并进客户端配置，改掉 `base-url` 和 token：

   | 客户端 | 配置文件 |
   |---|---|
   | Claude Code（按项目） | 项目根目录的 `.mcp.json` |
   | Claude Code（全局） | `~/.claude.json` 的 `mcpServers` |
   | Claude Desktop | `~/Library/Application Support/Claude/claude_desktop_config.json` |
   | Cursor | `~/.cursor/mcp.json` |

   `command` 要指向**编译好的二进制**（`go build -o cligc ./cmd/cligc`），
   不要写 `go run`——MCP 走 stdio，`go run` 的编译输出会混进协议流。

   token 通过 `env` 传，不要放进 `args`：`args` 会出现在进程列表里。

   **`.mcp.json` 里是明文 token，已经加进 `.gitignore`。**

3. 把 `skill/cligc-publish/` 放进客户端的技能目录
   （Claude Code：`~/.claude/skills/` 或项目的 `.claude/skills/`）。

远程客户端也可以直连 HTTP 传输：`POST https://你的域名/mcp`，
带 `Authorization: Bearer <token>`。

MCP 给的是**能力**，技能包给的是**规范**。只装 MCP 不装技能包，
AI 能发文章，但写出来的东西不会符合你站点的调性。

## 二开

改之前先跑一遍 `go test ./...`。仓库里有一批 lint 型测试专门守着容易踩的
边界（样式分层、滚动条、CSP、词表完整性），它们会在你改坏东西的当场报出来，
而不是等到几个月后才发现。

### 换外观

| 想改 | 改哪儿 |
|---|---|
| 配色、字号、间距 | `internal/web/static/base.css` 顶部的设计令牌 |
| 公开页的版式 | `internal/web/static/site.css` + `templates/partials_site.html` |
| 后台的版式 | `internal/web/static/admin.css` |
| 公开页模板 | `templates/{index,list,post,search}.html` |

**改公开页动不到后台，反之亦然**——两边只共享 `base` 那一层。往 base 里加
东西之前先问一句：这个是不是真的两边都要。`TestStyleLayersStaySeparated`
会拦住写错层的规则。

### 换品牌

`-title "你的站名"` 就够了。站名不以 `cligc` 开头时，字标（SVG 路径）
整个不出现，走纯文字——fork 过去改个名字不用动任何代码。

站标是 `templates/layout.html` 里的两个圆，直接改 SVG。

### 加一种界面语言

```bash
cligc lang new ja          # 生成模板
cligc lang check           # 看覆盖率和缺哪些 key
```

放进 `internal/i18n/locales/`（编进二进制）或用 `-lang-dir` 从外部加载。
覆盖率到 80% 才会出现在切换器里。

### 加一个页面

1. `internal/web/templates/你的页面.html`，第一行 `{{define "content"}}`
2. `internal/web/web.go` 的 `Routes` 里注册路由
3. handler 里调 `s.render(w, r, "你的页面.html", page{...})`

模板会自动被装配（glob 扫的 `templates/*.html`），不用登记。

### 改数据结构

加列走 `internal/store/db.go` 的 `migrate()` **第一阶段**，依赖新列的索引走
第二阶段——这两阶段不能合并，原因写在那个函数的注释里（合并了会让旧库
卡在半路启动不起来）。

`schema.sql` 是给新库用的，`migrate()` 是给已经在跑的库用的，两边都要改。

### 不建议动的地方

- `internal/api` 是全站唯一的写入口，网页后台和 MCP 都走它。
  绕过它单开一条写路径，意味着两套校验、两套权限判断，迟早有一套落后。
- `posts:publish` 和 `comments:moderate` 默认不发放这件事。
  想清楚再改——那两道闸门挡的分别是"AI 直接上线内容"和"prompt injection"。


## 设计取舍

这一节记录的是"为什么这么做"，改动前值得先读。

### 服务端渲染不是偏好，是前提

纯客户端渲染的页面要走 Googlebot 的二次渲染队列，延迟不可控，页面一多
基本抓不动。一个指望被搜索引擎收录的内容站，SSR 是入场券。
`html/template` + `embed.FS` 就够了。

### 哪些页面不进索引，是显式决定的

UGC 站最常见的索引问题不是"抓不到"，是"抓到太多低价值页面"，把整站
质量评分拖下去。所以：

| 页面 | 是否进索引 |
|---|---|
| 文章页（已发布、允许索引、无站外 canonical） | ✅ 唯一真正要收录的 |
| 首页第 1 页 | ✅ |
| 首页第 2 页及以后、标签页、作者页翻页 | ❌ `noindex,follow` |
| 站内搜索结果页 | ❌ 且 robots.txt 屏蔽 |
| 草稿、设了站外 canonical 的转载 | ❌ |

`noindex,follow` 的含义是「这页本身别收录，但内链照常传权重」——
聚合页正是这个用途。sitemap 只放文章本体，把抓取预算集中到值得的地方。

### 用户内容里的外链一律 `rel="ugc nofollow noopener"`

goldmark 渲染时自动加，不依赖作者自觉。不做这件事，站点会很快变成
外链农场的宿主。

### AI 只能写草稿

这条是架构级的，不是配置项：

- `posts:write` 只能创建草稿，`create_draft` 接口根本没有发布路径
- 发布需要独立的 `posts:publish` scope，默认不发放
- 即便有了 scope，还有每人每日发布上限（`-daily-cap`，默认 5）
- 写操作另有每分钟限速，防止 AI 进入循环刷出几千篇草稿
- 每篇记录 `source`（human / ai-assisted / ai-generated）和发布事件的
  `actor`（web / api），事后分得清什么是从 AI 客户端发出去的

原因：搜索引擎判定「规模化内容滥用」不看内容是不是 AI 写的，只看批量
程度和质量。AI 技能包让批量生产变得极其容易，把闸门做在服务端，比依赖
自制力可靠。

### 站点开哪些语言由站长定

内置 11 种语言，但「词表翻译完整」和「这个站对外提供这个语种」是两回事。
默认只开默认语言，其余在后台「站点」页逐个勾。

没勾的语言前缀直接 404，也不进切换器、不进 hreflang、不进 sitemap。
这不是洁癖：内容是按语言过滤的，站上只写中文时 `/de/` 是一个**空列表页**。
照着词表发 `hreflang="de"`，等于主动告诉 Google「这里有德语版」，然后
递给它一个没有任何文章的页面。不提供这个语种，比提供一个空的好。

勾选框旁边显示该语种已发布多少篇——勾之前先看见那边有没有东西。

**后台自己不受这个开关限制**（`isAdminPath`）。管理界面用哪种语言是站长的
个人偏好，和站点对外提供哪些语言无关；把 `/en/admin` 一起 404 掉的话，
一个只发中文的人就没法用英文界面了。这个坑踩过一次。

### 站名和描述：按语言各一份，三层优先级

    命令行 -title / -desc          部署时定的兜底值
    后台「站点」页                  站长随时改的，**每个语言一份**
    词表 site.title/description    想让文案跟着翻译一起进版本库时用，放 -lang-dir

按语言存而不是只存一份：`<title>` 和 `meta description` 直接进搜索结果，
英文页挂着中文标题，那一版的搜索结果就等于作废。取值时先找当前语言，
找不到退回默认语言，再找不到才用命令行的值。

只开一种语言时，表单收起「哪个语言」那层外壳（小标题和竖线），看起来和
以前一样；勾上第二种的那一刻才出现。单语言站是常态，不该替多语言站买单。

词表那一层用 `i18n.Own` 而不是 `i18n.T`：`T` 会回退到默认语言，于是
`-lang-dir` 里只给中文写了一条 `site.title`，英文页就会拿中文那条去盖掉站长
填的英文站名——一个只想给中文站起名的人，把英文站的名字也改了。词表只该
管它自己声明了的那个语言。

**内置词表刻意不带这两个 key。** 带了的话，站长在后台输入的名字会被内置
文案无声盖掉——那是在替别人的站做主。这个坑踩过一次：内置词表原本带着
`site.description`（描述的是 cligc 自己），而词表优先级最高，结果是后台改了
描述、10 种语言下看到的仍然是 cligc 的宣传语，还不报错。有测试守这条。

站点名称和描述放在「站点」页而不是「账号」页：那一页管的是作者资料
（显示名和简介会出现在文章署名行上），和站点是两回事。

### 首页的 hreflang 来自语言开关

文章页的多语言对应关系靠译文分组一篇篇连起来。首页没有那个东西，但它的
对应关系是**定义**出来的：站点开了哪些语言，那几个首页就互为版本。

所以这件事直到语言由站长显式声明才做得了。在那之前「站上有哪些语言」是
词表的属性，照着发 hreflang 等于替十种语言的空列表页做担保。

只在第 1 页发：`/en/?page=2` 不是 `/?page=2` 的译版——两边文章数不一样，
第 2 页装的根本不是同一批文章。

### 图片：一律转 WebP，尺寸写进库

上传的图片在落盘前过一遍 `internal/imaging`：解码 → 超过 `-img-max`（默认
2560）就按长边等比缩 → 编码成 WebP。

做这件事的理由是实测出来的账，不是"WebP 比较新"：

    1600×1000 照片 JPEG(q85) → WebP q80      -52%
    真实截图 PNG            → WebP           -95%
    大片纯色的 PNG          → WebP 有损      **+26%**

最后那一行是关键。有损编码器最不擅长的就是硬边和纯色块，所以按来源挑
编码方式（JPEG 只试有损——无损 WebP 是在无损保存 JPEG 的压缩瑕疵，实测
比原图大 390%；PNG/GIF 两种都试取小的），**编完再跟原图比一次大小，
没变小就原样留着**。宁可少省一点，也不要出现"上传之后文件变大了"。

不碰的两种：多帧 GIF（`image.Decode` 只给第一帧，转完就是把内容删了），
以及解不开的文件——后者直接拒收，MIME 是客户端说的，做不得数，而
`/media` 和站点同源。

解码前先读文件头看像素数（上限 4800 万）。一个几十 KB 的 PNG 可以声明
30000×30000，解出来要 3.6 GB——等 `image.Decode` 返回再检查就晚了。

顺手把宽高存进 `media` 表，正文里的 `<img>` 和封面都据此写 `width`/
`height`。没有它，图片下载完会把下面的正文整段往下顶，长文里每张图顶
一次。这是 CLS 最常见的来源。

**编码器是纯 Go 的。** `github.com/gen2brain/webp` 把 libwebp 从 wasm 转译
成 Go，`CGO_ENABLED=0` 能编，代价是二进制大 5 MB、1600×1000 编一次约
350 ms。构建时**必须带 `-tags nodynamic`**：不加的话运行时会先试着 dlopen
系统的 libwebp，而我们要用它去解码陌生人上传的图片，服务器上那份是什么
年份的没人保证（CVE-2023-4863 就是一个解码器堆溢出）。

给正文里的图加属性走的是 goldmark 的 AST transformer，和站外链接加
`rel="ugc nofollow"` 是同一处。尺寸靠一个 `SizeLookup` 函数注入——
`render` 不该知道数据库的存在，它只需要"这张图多大"这一个答案。

升级之后跑一次 `cligc rerender`：它先给存量图片补上像素尺寸（尺寸这一列
是后加的，老库里全是 0），再重刷文章 HTML。顺序不能反——正文里的
`<img>` 是在重刷的那一刻去查尺寸的，先刷 HTML 再补尺寸等于这次白刷，
而人不会想到要再跑一遍。补尺寸只读文件头，不重新编码：转码是有损的，
对着已经存进库的图再来一遍，是拿画质换一个这里根本不需要的东西。

### 封面：一张图，四个地方用

`posts.cover_media_id` 指向媒体库，`on delete set null`——在媒体库里删掉
一张图，该掉的是封面，不是文章。

同一张图出现在：列表卡片（左侧缩略图）、精选卡片（顶部横图）、文章页
标题下方、以及分享到社交平台时的 `og:image`。头条那张是整栏宽的，用
1200/630 铺开有 320 px 高，第一屏会变成「一张图加半个标题」——所以它
单独压成 5:2 的横幅，这一页的主角是标题。最后一个是唯一必须用绝对
地址的：抓分享卡片的爬虫不在这个域名下。没有封面时 `twitter:card` 保持
`summary` 而不是 `summary_large_image`——声明了大图却不给图，平台会去
正文里自己找一张凑数，找到什么全看运气。

后台里真正被提交的是一个原生 `<select>`，缩略图那套是 JS 套在外面的一层。
关掉 JS 剩下一个按文件名选图的下拉——朴素，但能用。当前封面即便已经翻出
了"最近 60 张"的范围也会被塞进候选列表，否则打开一篇旧文章、一保存封面
就没了。

正文插图有三条路：按钮开弹窗、把图拖进正文、直接粘贴。三条走同一个上传
口（`POST /admin/media.json`），做成三套只会有三套 bug。

### 站点设置：每一块自己保存

这一页拆成了几张独立的表单（语言 / 站点信息 / 搜索平台 / 评论 / 统计 /
资料），各自一个保存按钮，改动了才出现。服务端按 `section` 字段"改哪块
动哪块"：从当前设置出发，只覆盖这次提交的那一块。

必须这样是因为一次请求只带一块的字段。照旧整份覆盖的话，统计那张表单里
没有 `comments`，`r.FormValue("comments")` 得到空串——**改一次 GA4 ID
就把评论关了**，而且不报错。同一类错还有两处：单人站保存显示名会抹掉
简介、分类行保存会把顺序挪到最前。三处的判据都是"字段不在这次表单里，
就别动它"。

保存按钮是**可见**地渲染出来的，由 JS 在没有改动时收起来。反过来写
（默认 hidden、有改动才显示）的话，关掉 JS 就永远看不到保存按钮，这一页
整个变成只读的。

「账号」「API Token」「分类」原先各占一个标签页，都并进了这一页——它们都在
回答"这个站怎么配"。顶部导航从七个标签收到四个：**文章 / 评论 / 媒体库 /
设置**。三个老地址（`/admin/profile`、`/admin/tokens`、`/admin/categories`）
保留为跳转：它们可能在书签里，直接 404 会让人以为功能被删了。

页面结构是"表单在上、表格在下"：`.settings` 容器按"一栏表单"封在 34rem，
而分类和 token 都是宽表格，放在它外面。不为了排成别的顺序把容器拆开
又拼回去。

分类那一块的语言清单和站点文案那一块**不是同一份**：文案要列出全部语言
（没开的用 `data-langoff` 藏着，勾上就当场出现），分类是一张已经存在的
表格，没开的语言不该多出一列。

### 板块是一套结构配多份名字

板块（分类）回答"这个站分几块"。结构在各语言之间是同一套，要翻译的只有
名字——所以是**一个板块配多份名字**（`category_i18n`），不是每种语言各建
一套板块。

后者听起来更彻底，实际更糟：`/c/essays` 和 `/en/c/essays` 会变成互不相干
的两个东西，在板块页上切语言也就没地方可去。现在 slug 是共用的，切语言
就是换一份名字。

只存非默认语言，默认语言那一份仍在 `categories.name` 上，取值时先找译名
表、找不到退回去——和站名同一套路，也省掉一次迁移。译名行存在但留空等于
没翻，照样退回（`nullif`），不会显示一个空标题。

两处容易漏的：

- **文章卡片上的板块标签**按**这篇文章自己的语言**解析（join 用 `p.lang`）。
  不是页面的语言——一篇文章只有一种语言，也只出现在那种语言的页面上。
  漏掉它的表现是英文首页的卡片上写着「随笔」。
- **侧栏只列当前语言下有文章的板块**。全站口径的话，英文站的侧栏会写着
  「随笔 9」，点进去一篇都没有——那比不显示这个板块更糟。

### 分类顺序只能拖

表格里原先有一列"排序"数字框，是给没有 JS 的情况留的退路。拿掉了：两个
入口做同一件事，而那一列天天占着地方，只为一个几乎不会发生的情况。没有
JS 时顺序保持不变，不会乱。

代价是 `CategoryInput.Sort` 必须是 `*int`——行表单不再带这个字段，而
"字段不在表单里"和"用户填了 0"必须分得开。分不开的话，改一次板块名就把
它挪到最前面。

### 表单不能写在 <tr> 里

分类页每一行是一张编辑表单，但 `<form>` 本体放在表格**外面**，行里的控件
用 `form="cat-3"` 指过去。

这不是风格问题。HTML 的表格解析规则不允许 `<tr>` 里直接出现 `<form>`：
外层已经有一张表单（拖动排序那张）把"表单指针"占住时，这些 `<form>`
开始标签会被**整个忽略**——DOM 里根本没有那个 id，行里控件的 `.form`
全是 `null`，点保存什么都不会发生。页面照常渲染，控制台一声不吭。

这个坑踩过：给分类表格加拖动排序时把它包进了 `#reorder`，从那一刻起
每一行都存不下来了，直到几个版本之后才发现。有一条模板 lint 守着
（`TestNoFormInsideTableRow`），只查直接挂在 `<tr>` 下的——放在 `<td>`
里是合法的。

### 作者页只在多作者时才存在

`/u/{slug}` 列的是某个作者的文章。单人站上它和首页是同一批内容——
对读者是一条通向同样东西的多余链接，对搜索引擎是重复内容。

所以按 `count(*) from users` 自动切换：

- **一个作者**：署名是纯文字不链接，后台不显示「主页地址」和「简介」
  两个字段（它们唯一露面的地方就是 `/u/{slug}`），`/u/{slug}` 本身
  `noindex`。表单里没有的字段，保存时保持原值——不这么做的话，改一次
  显示名就会把简介抹掉、slug 按新名字重算，旧地址从此 404
- **多个作者**：一切照旧

路由在两种情况下都保留。已经存在的外链和书签不该因为站上少了一个人就断掉。

这也是为什么 postcard / featured-card 收的是 dict 而不是 store.Post——
它们要知道「现在是不是多作者」，而那是页面级的信息，不在文章上。

### 分类和标签是两个维度

| | 分类 | 标签 |
|---|---|---|
| 数量 | 少，稳定 | 多，随手加 |
| 一篇有几个 | 最多一个 | 任意多个 |
| 回答什么 | 这个站分几块 | 这篇讲了什么 |
| 出现在 | 顶部导航、署名行 | 文末、侧栏 |
| 排序 | 手动（`sort` 字段） | 按名称 |
| URL | `/c/{slug}` | `/t/{slug}` |

分类单独一张表而不是复用 `tags`，是因为它要的两件事塞进标签都别扭：
**手动排序**（导航顺序该由人定，不是按字母）和 **posts 上一个明确的外键**
（一篇只能属于一个板块）。

两条实现上的决定：

**`posts.category_id` 是 `on delete set null`，不是 cascade。** 删一个分类
只是整理导航，底下的文章会变成"未分类"，一篇都不会少。这两件事的后果差了
几个数量级，不该因为一次误点就混在一起——有测试专门守这条。

**分类页和标签页一样 `noindex,follow`。** 分类的价值在导航，不在被收录：
让读者知道"这个站分几块"，而不是让搜索引擎多抓几个薄聚合页。这一条是
一行的事，想让它进索引就把 `handleCategory` 里的 `NoIndex` 去掉。

**分类计数只算已发布的。** 导航上写着"随笔 3"、点进去只有 1 篇
（另外 2 篇是草稿），这种数字比不显示更糟。

### 文章有三种状态，归档不是软删除

| 状态 | 列表 / 搜索 / sitemap | URL 可访问 | 索引 |
|---|---|---|---|
| `draft` 草稿 | ❌ | 仅作者与管理员 | ❌ |
| `published` 已发布 | ✅ | 所有人 | ✅ |
| `archived` 已归档 | ❌ | **所有人** | ❌ |

归档的用途是「从列表和索引里撤下，但不让已有链接失效」。把它做成 404
会让已经被收录、被别人引用过的文章统统变成死链，那比继续挂着更糟。

发布必须走 `PublishPost`（它要过每日配额、要记审计事件）；`SetStatus`
刻意只接受 `draft` 和 `archived`——权限检查最怕的就是留一条绕过它的后门函数。

### SQLite 的几个必需动作

- **WAL 模式**。不开的话读写互相阻塞，一个慢查询能卡住写入。
- **写池 `MaxOpenConns(1)`**，读池独立。SQLite 单写者，把排队交给 Go 的
  连接池，而不是让 SQLite 抛 `database is locked`。
- **`busy_timeout=5000`**、`foreign_keys=ON`（默认是关的）、
  `synchronous=NORMAL`。
- **Litestream**。见 `deploy/litestream.yml`，第一天就配。

### 中文全文检索

FTS5 内置的 `unicode61` 把 CJK 当成 alphanumeric，一整段中文会变成
**一个 token**，中文检索直接失效。

这里的做法是写入前做 **bigram 切分**再用空格隔开（`internal/tokenize`），
查询端同样切分并拼成 FTS5 短语，效果接近子串匹配。

相比引入词典分词（jieba/gse）：零依赖、零词典、结果确定，不会因为词典
更新导致新旧索引不一致。代价是索引体积约为原文 2 倍。

检索结果的摘要高亮**不用** FTS5 的 `snippet()`——索引里存的是二元组，
`snippet()` 输出会变成「这篇 篇文 文章 章讲」这种每个字重复两遍的东西。
高亮在原文上另算（`render.Highlight`），所以 `posts` 表多存了一列
`body_text`。

### 面向 AI 的接口和面向浏览器的不一样

同一套 REST API，但有三条额外约束：

1. **省 context**：列表和搜索结果**不含正文**，要正文得显式传 `full=true`。
   一篇 5000 字的文章就是几千 token。
2. **幂等**：`create_draft` 必须带 `idempotency_key`，24 小时内同 key 复用
   首次创建的文章。AI 客户端会重试。
3. **错误信息写给模型看**：MCP 层把 API 错误码翻译成"下一步该怎么办"。
   比如缺发布权限时返回的是「草稿已保存，让人去后台发布，不要重试」，
   而不是一个 403。

### 代码高亮走 class，不走内联样式

chroma 默认给每个 token 写 `style="color:#..."`，而站点的 CSP 是
`style-src 'self'`——那些内联样式会被**整段拦掉**，代码块退化成一片白字，
且浏览器不报任何可见错误。所以用 `WithClasses(true)` 让它输出 Pygments
标准短名（`.k` `.s` `.nf`…），配色写在 `app.css` 里，顺带也能跟着站点的
明暗主题走。

代码块结构是 `<div class="codeblock" data-lang="go"><pre class="chroma">`：
分两层是因为语言标签要固定在右上角，而 `pre` 自己是横向滚动容器，
标签放进去会跟着内容滑走。

不开启语言猜测：猜错了比不高亮更难看，而且猜测要跑一遍所有 lexer。

### 多语种

语言菜单在导航栏，是个下拉。服务端渲染的是**几个并排的链接**——没有 JS
时那本身就是完全可用的形态，`app.js` 只是把它折起来省掉横向空间，
不需要任何降级分支。按钮的内容直接搬运服务端渲染好的那份（地球图标 +
当前语言名），不在 JS 里重拼一遍——重拼的那份迟早和模板走偏。

`/` 是中文，`/en/` 是英文。**不对称**（默认语言不带前缀）：保住已有 URL、
主路径少一跳重定向、域名权重不分散（这点比 `en.cligc.com` 子域名强）。
`/zh/…` 301 回 `/…`，避免同一内容两个地址。

**绝不按 `Accept-Language` 自动跳转。** Googlebot 基本只用一种 locale 抓取，
自动跳转会让它永远只看得到一个版本，另一个语种等于不存在。

实现上只有**一个中间件**：`WithLang` 在 mux 匹配之前把 `/en/` 剥掉，于是
所有已有路由一条都不用改，也不会出现"每条路由注册两遍"那种必然漏掉
一两条的写法。模板里凡是站内链接都过 `{{lurl "/x"}}`，否则在 `/en/` 下
点一下就掉回中文站了。

#### hreflang 的三条规则，错一条整套失效

1. **必须互相引用**——每一版都要列出所有版本，**包括它自己**。单向标注会被
   Google 整体忽略，而且不报错。
2. **必须有 `x-default`**，指向默认语言那一版。
3. **每一版的 canonical 必须指向它自己。** 把译文的 canonical 指向原文，
   等于告诉 Google 别收录译文——整套多语种工作全部作废。这是最常见的错法，
   而且和站内已有的 `canonical_url`（站外转载用）语义正好相反，代码里分开处理。

`TestHreflangIsReciprocalAndSelfCanonical` 守着这三条。

#### 译文关系是「组」不是「主从」

`translation_key` 让同一内容的各语言版本共享一个值。不做父子结构：加第三个
语种时不用决定"它是谁的孩子"，删掉任何一篇也不会让其余版本变孤儿。现实中
英文版写得比中文版好是常事，没有哪个版本天然更"正"。

`Translations()` 只返回**已发布**的版本：hreflang 指向草稿或 404 比没有 hreflang
更糟，Google 会认为整组标注不可信而整体忽略。

#### 界面语言：50+ 种怎么撑住

关键在于**把内容语言和界面语言分开**。混为一谈就会得出"支持 50 种要写一万条
文案"的结论——实际上内容侧一条都不用写：

| | 数量 | 加一种的成本 |
|---|---|---|
| **内容语言** | 注册表里 60+ 种 BCP 47 标签 | 零。文章带个标签而已 |
| **界面语言** | 有目录文件的那几种 | 一个 JSON 文件 |

一篇斯瓦希里语文章完全合法，哪怕界面还没翻成斯瓦希里语。把两者绑在一起，
等于规定"界面没翻译过的语言不许发文"。

**文案存 JSON 数据文件，不存 Go 源码。** 加一种界面语言 = 丢一个文件，
不用改代码、不用重新编译：

```bash
cligc lang new ja > locales/ja.json   # 生成模板，值是中文原文，照着翻
cligc serve -lang-dir locales          # 启动时叠加到内置目录上
cligc lang check locales               # 看覆盖率和缺了哪些 key
```

外部目录是**叠加**不是替换：可以只写想改的几条，其余沿用内置。

**复数走 CLDR**（`x/text/feature/plural`）。自己写"n==1 用单数"那套只对英文
成立——俄语有四类、阿拉伯语有六类，而 0 在英文里是复数、在法语里是单数。
这些规则没有一个能靠直觉猜对。这也是当初说"两形式够用，真到 50 种再换 x/text"
的那个门槛，现在换了。

**逐条回退**：一个翻了 60% 的语言，那 60% 照常显示，剩下的用默认语言，
而不是整个语言不可用。50 种界面语言的现实就是完成度参差不齐。

**覆盖率门槛 80%**：没达标的语言仍然加载并逐条生效，但不出现在切换器里——
用户选了「Español」结果看到一半中文，比根本没有那个选项更糟，他会以为站点坏了。

覆盖率把**值和原文完全相同**算作未翻译。`lang new` 生成的模板把原文填进去
当占位，只看"有没有值"的话，一条没动的模板会显示成 100%——那个数字比没有
还坏。但「缺失」和「未翻译」要分开报：前者是硬缺陷（key 不在），后者是软信号
（可能是 `Slug`、`RSS` 这种合法同文）。

**RTL**：阿拉伯语、希伯来语、波斯语、乌尔都语在注册表里标了 `rtl`，
`<html dir>` 跟着走。漏标的话整个界面是镜像错乱的，而在一个只读中文的人眼里
完全看不出问题。

#### 语言切换器

超过 8 种就自动出过滤框。十来种靠滚动还能找，五十种不给搜索就等于让人一行行
扫——而且用户要找的那种语言，他多半只认得出**母语名**（한국어、العربية），
拼不出英文名。所以列表按母语名显示和排序，过滤同时匹配母语名和语言标签。

hover 和键盘高亮**共用同一个视觉**：鼠标移过去和按方向键挪过去，对用户是
同一件事"我现在指着这一项"，不该长得不一样。而"已选中"用颜色和 ✓ 单独标，
那是另一个维度。

#### 字标

`cligc` 画成 **SVG 路径**，不是用字体排版。字标一旦依赖系统字体，在 macOS、
Windows、Android 上就是三个样子——而字标恰恰是最不该变的东西。路径在哪都
一模一样，也不需要加载字体文件、不会有 FOUT。

几何取自站标：x 高圆半径 5、描边比例一致，两者是同一套形制。`i` 的点用
零长度线段配圆头端点画，直径自动等于描边宽，改粗细时不会出现"点和竖线
不一样粗"。

站名不以 `cligc` 开头时自动退回渲染纯文字（见 `splitBrand`）——fork 这个
项目改个名字不用动任何代码，也不会出现一个画着 cligc 却叫别的名字的站。

#### 界面 i18n 的其它约定

`internal/i18n` 是个 200 行的目录，**不引 `x/text`**：这里只需要按 key 取文案
和最小复数处理，而 x/text 的价值在 CLDR 的完整复数规则和本地化数字/日期格式。
中日韩没有复数变化，英文只有 one/other——两形式够了。真要加俄语（4 形式）
或阿拉伯语（6 形式）时再换，那时 Catalog 的形状本来也要改。

- 每个语言一套模板，**启动时各构建一次**。这样 `{{t "key"}}` 在任何地方
  （包括 partial）都能直接用，不必把页面对象一路传下去写成 `{{$.T "key"}}`。
  代价是几百 KB 内存。
- Go 侧的 flash 和错误页和模板**共用同一套目录**：两份目录必然走偏，
  而 flash 恰恰最容易被忘记翻译——它只在操作成功或失败的一瞬间出现。
- 漏翻的 key 会显示成 `admin.posts.title` 这种刺眼的原样字符串，而不是空白。
  `TestNoMissingTranslations` 在 CI 里直接失败，比让用户先看到强。
- 站名和描述是**可选覆盖**（`OptionalKeys`）：不写就沿用后台设置或配置值。
  站名往往是专有名词不该翻，描述几乎总该翻。取的时候用 `Own` 而不是 `T`，
  见上面「站名和描述」一节——这是这两个 key 和其它所有 key 的关键差别。

#### 一个还没解决的技术债

FTS 分词器对中文做 bigram，英文是整词通过但**没有词干还原**——搜 `running`
匹配不到 `run`。中文站感觉不到，认真做英文内容就会暴露。要么接受，
要么给英文单独接一个 Porter stemmer。

### 全站一个容器宽、一个内容栏宽

曾经列表页用 46rem、文章页用 56rem，结果内容的**左边缘在页面间跳了 80px**、
内容宽度也差 80px——两个维度同时变，切页时整块内容在挪位置。

现在统一：容器 56rem，内容栏 38rem（约 36 个汉字一行），右侧 16rem 是侧栏。
文章页侧栏是大纲，列表页是标签。实测每个页面内容都落在同一区间：

```
首页    209..817 (608px)   侧栏 865..1057
文章页  209..817 (608px)   大纲 865..1057
```

标签放侧栏不只是为了填空：它既是给读者的导航，也是给爬虫的站内链路——
标签页本身 noindex，但它把权重继续传给文章页。

### 文章页：加宽的是容器，不是正文

38rem 一行约 36 个汉字，是中文长文最耐读的区间。所以加大纲时**容器从 46rem
放到 56rem，正文栏宽一个像素没动**——右边多出来的空间给导航用，而不是把
文字拉宽。这两件事经常被混为一谈。

放不下两栏时（< 62rem）直接收起大纲并把正文居中。挤成一条窄栏的目录比没有
目录更难用；而单栏时如果还靠左，右边会空出一大块，看起来像布局塌了。

大纲**服务端渲染**，不靠 JS 生成：爬虫能看到章节链接（有机会产出"跳转到章节"
的站内链接），关掉 JS 的人也还有目录可用。JS 只负责"当前读到哪一节"的高亮，
那才是纯粹的增强。少于两条小标题时不出大纲——一条目录不提供导航价值，
却要占掉一整栏。

### 中文标题的锚点，以及一个静默失效的坑

goldmark 默认的 ID 生成器遇到多字节字符**直接跳过**，纯中文标题因此产出空串、
退化成 `heading`、`heading-1`、`heading-2` 这样的按序编号。

后果是：**在文章中间插入一个新标题，它后面所有已经被分享出去的深链会全部
静默错位**——页面照常打开，只是跳到了别的段落，没有任何报错。

所以 `internal/render/headings.go` 换掉了这个生成器，保留 CJK 字符：
`## 三条路` → `#三条路`。现代浏览器在地址栏里会显示成中文，分享出去可读；
更重要的是它只跟标题内容有关，重排、增删其它标题都不影响它。
`TestHeadingIDsSurviveReordering` 守着这条。

注意 `parser.WithIDs` 是**上下文**选项不是解析器选项，要在 `Parse` 时传入，
而 `WithAutoHeadingID()` 得留着——前者决定"怎么生成"，后者决定"要不要生成"。

### 首页第一屏：用内容宣传，不用文案

首页**没有**大幅的自我介绍。理由不是审美，是三条事实：

1. **首页不是落地页。** 内容站 90% 以上的自然流量直接落在文章页——有人搜
   「SQLite 中文检索」，Google 把他丢到 `/p/sqlite-fts5`，他从头到尾没见过
   首页。把第一屏花在宣传上，是在优化一个绝大多数人的第一印象根本不经过的页面。
2. **会看首页的人都不缺上下文。** 回头读者要「有什么新的」，从文章点过来的
   要「还有什么别的」，爬虫要指向内容的链接——宣传屏对这三者都是障碍。
3. **内容站的产品就是内容。** SaaS 需要 hero 因为产品看不见；一句
   「欢迎来到 XX」回答不了「这站水平如何、值不值得留下」，三个真实标题
   五秒钟就回答了。

所以第一屏是 137px 的抬头（站名 + 一句话定位）+ **精选区**：一篇头条
（大标题 + 完整摘要）加两篇并排的次条。这是一个**由内容构成的 hero**，
额外好处是把站内权重集中到了最好的几个页面上——宣传文案做不到这点。

精选的实现要点：

- `featured_at` 存时间戳而非布尔值，非空即精选，同时天然给出排序依据
  （刚置顶的排在前面），不用再加 order 字段
- **只有已发布的能被精选**：精选区是首页最显眼的位置，草稿出现在那里
  等于绕过了发布闸门
- 精选文章从**所有**分页里排除。只在第一页排除的话，翻到第二页会看到
  同一篇再出现一次，而且总数对不上导致分页错位
- 超过 3 篇仍可标记但不展示，后台如实显示「已精选 N 篇，首页展示前 3 篇」——
  比在置顶时报错让人猜"为什么不让我加"要好
- 布局是一大两小而不是三等分：46rem 的栏宽里三列每列只有 245px，放不下摘要

**没有开放给 API / MCP。** 置顶是策展决定，和审核评论同一类——把陌生人或
AI 的判断放到首页最显眼的位置，必须是人点的。

### 数据库迁移：两阶段

`schema.sql` 全是 `create ... if not exists`，对全新的库是完整的，但**对已经
存在的库，新加的列不会被套用**——建表语句直接跳过了。所以 `Open()` 在跑完
schema 之后还会跑一遍 `migrate()`：

1. 第一阶段补列（`alter table ... add column`）
2. 第二阶段建**依赖这些新列的索引**

必须分开两阶段。这类索引不能写进 `schema.sql`：那个文件整体跑在补列之前，
在旧库上 `create index` 会因为列还不存在而失败，**并连带把后面的
`alter table` 一起挡掉**——结果是库卡在半路、服务直接起不来。
这个坑是实打实踩过的，`TestMigrationAddsColumnToExistingDB` 守着它。

迁移助手刻意**只支持"加列"**，不做通用框架：真要改列类型或删列时，SQLite
本来就得走"建新表-搬数据-换名"那一套，那种改动值得单独写清楚，不该藏在一个
看起来什么都能干的助手函数里。

### 站标：两个圆

一个描边圆 + 一个实心圆错位相交。空心是草稿、实心是已发布，交集是人和 AI
一起完成的那部分——这个站的核心结构正好是这个形状。

导航栏里是**内联 SVG**（不多发一个请求，两个圆各自取色所以能跟着明暗主题走），
`static/favicon.svg` 则是带深色圆角底的方版。两者形状一致但不能共用一个文件：

- 导航栏的标记画在页面背景上，描边圆用 `--line-strong` 才能"弱"下去
- favicon 画在**浏览器标签栏**上，而标签栏底色随系统主题和浏览器而变。
  不带底色的话，浅色描边在浅色标签栏上会直接消失

小圆会**朝着光标的方向绕环公转**。三个实现上的约束：

- `viewBox` 是 34 而不是刚好框住图形的 32——轨道整圈都得在画布内，
  否则小圆转到左边就被裁掉。渲染尺寸按同比例放大，静止时的视觉大小不变。
- 改的是 SVG 的 `cx`/`cy` **几何属性**，不是 CSS transform。站点 CSP 是
  `style-src 'self'`，动内联样式是给自己找麻烦。
- 触屏（没有"光标方向"可言）和 `prefers-reduced-motion` 下直接不启用，
  小圆停在设计稿的静止位。

顺带：`/favicon.ico` 单独返回 204。浏览器每次首访都会自动请求它，没有这条
路由就会落到兜底 404，让每个访客白下载一整页 HTML。

### 静态资源带内容指纹

`embed.FS` 里的文件 modtime 是零值，`http.FileServer` 因此**既发不出
Last-Modified 也发不出 ETag**。没有验证器又没有 `Cache-Control`，浏览器
既无法条件请求、也无法安全缓存——结果是每次访问都把 40KB 的 CSS+JS
重下一遍，而这种浪费不以任何形式报错。

所以引用一律走 `{{asset "app.css"}}`，输出 `/static/app.css?v=<内容哈希前10位>`，
`/static/` 则打 `immutable` 长缓存。内容一变 URL 就变，老 URL 不会再被请求，
新 URL 必然是新内容——比"短缓存 + 每次条件请求"省一个往返，也不会有
部署后拿到旧 CSS 的问题。

### 后台：区分"用来读的字"和"用来点的控件"

正文 17px 是为了读着舒服，但按钮、筛选器、下拉跟着用 17px 就显得笨重。
所以有一档 `--t-ui: 0.875rem`（14px）专门给界面控件。

唯一的例外是**真正要打字的字段**（标题、正文、简介）——它们保持 16px，
因为 iOS Safari 对小于 16px 的输入框会在聚焦时自动放大整个页面。
"点的控件"和"打字的字段"这条分界比"全站统一字号"更重要。

控件高度的主要来源是**行高**而不是字号：单行控件里没有"段落"可言，
沿用正文的 1.7 只会让框白白长高一截。基础控件走 1.4，多行 textarea 保留
1.7。定下来的层级是：

| | 高度 |
|---|---|
| 公开页主动作（搜索页输入框、提交按钮） | 40px |
| 后台文本字段（标题、slug、名称） | 36px |
| 后台控件（按钮、下拉、筛选器） | 31px |

触屏上另有 `@media (pointer: coarse)` 把点击区域补回来——桌面鼠标不该
为触屏的指点精度付出版面代价。

其它几条：

- **所有后台页面共用 `--w-wide`**。编辑页原本没打 Wide 标记，从「管理」点进
  「编辑」容器宽度会跳变。编辑区内部另有 `.admin-narrow` 限宽（一行 120 字符
  的 Markdown 不好读），但**标题栏必须一起限**，否则右边会差出一截。
- **textarea 默认走正文字族**。简介、摘要、评论都是散文，用等宽字体既难读
  又在暗示"这里要写代码"。只有 Markdown 编辑区才等宽——那里要对齐代码块和表格。
- **复选行整行可点**：padding 放在 `<label>` 上，点击区域从"那个 12px 的小方块"
  变成一整行。

### 提示框组件，以及 CSP 下能改样式的那条窄路

后台的行内操作（查看/发布/撤下、通过/标为垃圾/退回待审/删除、吊销）全部
换成了图标按钮。理由是：审核页上真正要读的是评论正文，一排文字按钮会把
视线从内容上拽走；图标退成一排安静的符号，语义交给 tooltip。

每个图标按钮都写两个属性，缺一不可：

- `aria-label` —— 给辅助技术和无 JS 环境。图标按钮没有可见文字，
  漏写它就是个无名控件，而这种缺陷在视觉上完全看不出来
- `data-tip` —— 给鼠标用户看的提示

提示框是全站共用的一个元素，挂在 `<body>` 下。**不用 `::after` 画在触发
元素上**，因为表格外面套着 `overflow-x: auto`（横向滚动用），伪元素会被
那一层裁掉；`position: fixed` 的独立元素不受任何祖先裁剪影响。

坐标怎么传，取决于一条实测出来的 CSP 行为。站点 CSP 是 `style-src 'self'`：

| 写法 | 结果 |
|---|---|
| `el.style.left = '42px'` | ✅ 生效 |
| `el.style.setProperty('--x', …)` | ✅ 生效 |
| `el.setAttribute('style', …)` | ❌ **被静默拦掉** |

最后一种不报错、不抛异常，只是样式不生效——写的人完全看不出问题在哪。
所以提示框只通过 CSS 自定义属性喂两个数字（`--tip-x` / `--tip-y`），
真正的样式全留在样式表里。`TestNoStyleAttributeWritesInJS` 守着这条。

### 自定义下拉，原生 select 留在表单里

原生 `<select>` 展开后的列表由操作系统绘制，CSS 完全管不到——字号、间距、
圆角、选中态全都跟站点其余部分对不上。所以 `app.js` 在它外面套一层可见的
按钮 + 列表。

原生控件本身**留在表单里**（只是移出视觉流），三个理由：

- 关掉 JS 时它就是一个完整可用的控件，不需要任何降级分支
- 表单提交走它，不用额外维护 hidden input
- 浏览器的自动填充、表单重置照常有效

可访问性上分开了两件事：按钮的 `aria-label` 是**用途**（"按状态筛选"），
按钮文字是**当前值**（"草稿"）——这正是原生 select 的播报方式。
列表里"键盘高亮的项"用背景色、"已选中的项"用左侧的勾，两者是不同的状态，
不能共用一种视觉。

### 前端：排版系统就是视觉身份

没有框架、没有构建步骤，整站一个 CSS 文件随二进制 embed。几条明确的决定：

- **字体栈「拉丁在前，CJK 在后」**。绝大多数中文站把顺序写反，结果英文
  单词被中文字体里的西文字形渲染，又宽又松。
- **底色不是纯白**。`#fff` 在长文阅读下偏刺眼，暖白更接近纸。
- **两个强调色**：墨蓝用于交互（链接、焦点），朱砂用于标记（`<mark>`、
  AI 来源徽章、危险操作）。朱砂让整站有中文排版的气质，又不至于把链接
  做成红色那种反直觉的东西。
- **三档栏宽**：正文 38rem（约 36 个汉字一行）、列表 46rem、后台 76rem。
  表格是密集信息，窄栏反而难用。
- **正文行距 1.85**。中文长文需要比西文更大的行距。
- 间距只用一套 4px 基准的尺度令牌，不出现 13px、27px 这种随手数字。

两个容易踩的坑，都已经踩过并修掉了：

1. `input[type="text"]` **不匹配没写 `type` 属性的 input**。表单里
   `<input name="title">` 这种省略写法极常见，逐个列举 `input[type=...]`
   会让它们悄悄漏掉样式。所以基础规则用排除法匹配。

   **但排除项必须包在 `:where()` 里**——这是修完第一个坑之后紧接着踩的
   第二个：`:not()` 会把参数的特异性累加上去，裸写五个 `:not([type=...])`
   让这条"默认样式"变成 `(0,5,1)`，反过来压死了 `.nav-search input` 这类
   `(0,1,1)` 的组件级覆盖——导航栏搜索框的宽度、内距、圆角、边框色**全部
   失效**，而 CSS 不报任何错。`:where()` 的特异性恒为 0，基础规则退回
   `(0,0,1)`，任何类选择器都能干净覆盖。
   `TestBaseInputRuleHasZeroSpecificity` 守着这条。
2. CSP 是 `style-src 'self'`，**页面里不能有任何 `style=` 属性**。所以
   后台的发布配额用「离散小格」而不是百分比宽度的进度条——格子数就是配额数，
   一眼看得出还剩几篇，也不需要内联样式。

### 评论：纯文本、匿名必审、AI 只能隐藏不能放行

评论正文**按纯文本存储和渲染**——不解析 Markdown，不自动识别 URL，
不生成任何可点击链接。这个站的整个论点就是「别变成外链农场的宿主」，
而评论区是最经典的灌链入口，把这道口子焊死的收益远大于允许富文本。

| 来源 | 结果 |
|---|---|
| 登录用户 | 直接通过（站上的账号都是自己开的，不是开放注册） |
| 匿名访客 | 进 `pending` 队列，人工审核后才显示 |

另外有蜜罐字段（命中即**静默丢弃**，让机器人以为得逞了，比返回错误更能
减少重试）和按 IP 的限速。`-comments=false` 关闭时，提交路由**根本不注册**，
而不只是把表单藏起来——藏起来的表单仍然可以被直接 POST。

**AI 侧默认只有一个方向。** `flag_comment_spam` 走 `posts:write`，因为标垃圾
只会让内容从公开页消失，随时能在后台退回——可逆的、只减不增的。

通过审核、退回、删除要单独的 `comments:moderate`，**默认不发放**，勾选时
界面上带红色警告。它和 `posts:publish` 是同一类闸门，但理由不同：

> 评论是站外任何人都能写进来的内容，而 AI 会把它读进上下文。给了这个权限，
> 等于允许「评论正文里写一句指令 → AI 照做」。这是 prompt injection 最标准
> 的形态，不是假想的攻击。

早先这里干脆不给接口——不给接口比给了再加权限检查更可靠。后来按需求把
全站功能都开放给了 API，于是改成一个独立 scope。**这是一次实打实的让步**：
现在的安全性取决于站长勾选时读没读那行警告，而不再取决于接口不存在。

### 刷评论：三道闸门，各挡一个维度

| 闸门 | 挡什么 |
|---|---|
| 限速 | 单个来源发得多快 |
| 队列上限 | 全站积压总量 |
| 内容去重 | 换了地址但照抄同一段文字 |

**限速必须按 IPv6 的 /64 聚合。** 运营商给一条家宽分配的就是一个 /64，
里面有 2^64 个地址——按完整地址限速，攻击者换一个地址就重置一次计数。
实测过：同一个 /64 里换 40 个地址提交，40 条全进；同一个 IPv4 地址提交
20 次，只进 3 条。登录那边是同一个洞，而且更严重（那是撞库）。

**队列上限（默认 500）挡的不是磁盘。** 队列被灌满之后真正的损失是，
一万条垃圾里混着的三条真人留言再也找不出来——评论功能等于废了。
满了就暂停接收匿名评论，站长清完自动恢复；登录用户不受影响，
他的评论直接通过、根本不进队列。

**重复内容按蜜罐的方式静默丢弃**（返回成功但不写库）。明确报错等于
告诉脚本「换段文字再来」。

### 评论是 prompt injection 的入口，按不可信数据对待

评论是陌生人写进数据库、然后会原样进入模型上下文的文本。如果模型把它当
指令读，一条评论就能指挥 AI 客户端做事。三道防线：

1. **字段名即提示词**。API 返回的字段叫 `body_untrusted` 和
   `author_name_untrusted`，不叫 `body`。叫 `body` 的字段读起来像"内容"，
   叫 `body_untrusted` 的读起来像"别信它"。
2. **独立的警示 content 块**。MCP 把警告作为第一个 content 块返回，模型是
   先读到它、再读到评论的。放在 JSON 字段里很容易被长篇内容淹没。
3. **握手时的 instructions**。用户没装技能包时，这是唯一到达模型的规则。

`internal/mcp/mcp_test.go` 里有测试锁住这三条。

### 安全

- 正文用 goldmark 渲染且**不开 Unsafe**，原始 HTML 一律转义
- 不接受 SVG 上传——SVG 能内嵌 `<script>`，而 `/media` 与站点同源，
  等于存储型 XSS。要支持得换独立域名托管
- `upload_media` 按**字节内容**嗅探类型，不信扩展名。这个工具能读本机
  任意路径，如果类型由调用方说了算，一段藏在网页里的注入指令就能诱导
  模型把私钥当 PNG 传上公网
- 改密码会**吊销该用户的全部会话**。改密最常见的动机就是怀疑被盗号，
  留着旧会话等于白改（当前会话会立刻重建，用户不会被踢出去）
- 后台上传同样按**字节内容**嗅探类型，不信浏览器声明的 Content-Type
- 登录接口按 **IP 和邮箱两个维度**限速（10 分钟 8 次）。只按 IP 挡不住
  分布式撞库，只按邮箱挡不住横向扫号；按邮箱那一维还不受反代配置影响
- CSRF 用 `SameSite=Lax` + `Sec-Fetch-Site`/`Origin` 校验
- 全站 CSP、`nosniff`、`Referrer-Policy`
- API token 只存 SHA-256，明文仅在创建时返回一次

## 命令

```bash
cligc serve  -addr :8866 -base-url https://example.com -daily-cap 5 [-trust-proxy]
cligc mcp    -base-url https://example.com          # CLIGC_TOKEN 走环境变量
cligc user  add    -email a@b.com -name 名字 [-admin]
cligc token create -email a@b.com -name 客户端名 [-scopes ...] [-days 90]
cligc rerender     # 渲染器变更后重刷全部文章的 HTML 缓存与全文索引
```

`body_html` 和全文索引都是 `body_md` 的派生物。加代码高亮、改外链规则这类
改动只影响新写的文章，老文章要靠 `rerender` 补上——这种"过时"不会报错，
只会表现为「新文章有高亮、老文章没有」。

所有参数都有对应环境变量：`CLIGC_DB` `CLIGC_ADDR` `CLIGC_BASE_URL`
`CLIGC_TITLE` `CLIGC_DESC` `CLIGC_MEDIA` `CLIGC_DAILY_CAP` `CLIGC_TRUST_PROXY`
`CLIGC_COMMENTS` `CLIGC_TOKEN`。

`-trust-proxy` 只在确实部署在自己的反向代理后面时打开：它决定登录限速
是否采信 `X-Forwarded-For`。无条件信任这个头，等于让任何人自选限速桶。

探活端点是 `GET /healthz`，它会真的 ping 一次数据库——只回 "ok" 而不碰 DB
的健康检查，会在磁盘满或文件被误删时依然报健康。

## 部署

```bash
GOOS=linux GOARCH=amd64 go build -ldflags "-s -w -X main.version=$(git describe --tags --always 2>/dev/null || echo dev)" -o cligc ./cmd/cligc
```

纯 Go（无 cgo），交叉编译一条命令出静态二进制。scp 上去，配好
`deploy/` 里的 systemd + Caddy + Litestream 即可。

## 持续集成与部署

两个工作流，在 `.github/workflows/` 下。

**`ci.yml`** —— 每次 push 和 PR：gofmt、vet、`go test -race`、构建、
JS 语法检查、词表完整性。

`-race` 不是摆设：这个站有三处共享状态（后台定时任务、限速器、设置缓存），
竞态最容易藏在那里。JS 语法检查也不是——前端没有构建步骤，没有任何东西
会在发布前解析那些文件，一个语法错会静默地让整页失去交互，而 Go 的测试
看不到它。

**`deploy.yml`** —— 合进 main 之后：交叉编译 linux 静态二进制 → scp 到
服务器 → `deploy/deploy.sh` 原子替换、重启、健康检查，**失败自动回滚**。

### 两条路线，选一条

**路线一：自托管 Runner（推荐）。** 在服务器上跑一个代理，它主动去 GitHub
拉任务。仓库里一个 secret 都不用配，服务器也不用对外开端口。

在服务器上以 root 执行一次：

```bash
git clone https://github.com/ccvar/cligc && cd cligc/deploy
REPO=你的用户名/cligc TOKEN=<从GitHub页面复制> sh setup-runner.sh
```

TOKEN 在 仓库 → Settings → Actions → Runners → New self-hosted runner
那个页面上，`./config.sh --token AXXXX` 里的 `AXXXX` 就是。它一小时内有效，
只用于注册这一次。

脚本会建一个专用用户、注册 Runner、装成开机自启的服务，并写一条
**只允许执行部署脚本一条命令**的 sudoers。

> ⚠️ 自托管 Runner 执行的是工作流里的代码。这个仓库的 `deploy.yml` 只在
> `push` 到 main 和手动触发时跑，**不在 `pull_request` 上跑**——否则任何人
> 提一个 PR 就能在你的服务器上执行代码。改这个触发条件前想清楚。

**路线二：SSH 推送。** 适合不想在服务器上跑 Runner 的情况。把仓库变量
`DEPLOY_RUNNER` 设成 `ubuntu-latest`，然后配这些 secret：

| Secret | 内容 |
|---|---|
| `DEPLOY_HOST` | 服务器地址 |
| `DEPLOY_USER` | 登录用户 |
| `DEPLOY_SSH_KEY` | 私钥（部署专用，不要复用你自己的） |
| `DEPLOY_KNOWN_HOSTS` | `ssh-keyscan 你的服务器` 的输出 |

`DEPLOY_KNOWN_HOSTS` 不是可选的。省掉它就得用 `StrictHostKeyChecking=no`，
那等于把这条通道对中间人敞开——而它手里有一把能替换服务器上二进制的密钥。

服务器上仍然要预先装好部署脚本：

```bash
sudo install -D -m 755 deploy/deploy.sh /usr/local/lib/cligc/deploy.sh
echo 'deployuser ALL=(root) NOPASSWD: /usr/local/lib/cligc/deploy.sh' \
  | sudo tee /etc/sudoers.d/cligc-deploy && sudo chmod 440 /etc/sudoers.d/cligc-deploy
```

### root 执行的脚本必须在仓库之外

两条路线都调 `/usr/local/lib/cligc/deploy.sh`，而不是 CI 里 checkout 出来的
那份 `deploy/deploy.sh`，sudoers 也只授权这一个绝对路径。

这不是绕远路：允许 root 执行仓库里的脚本，等于把「能往仓库推代码」直接
升级成「能在服务器上当 root」。改一行 `deploy.sh` 就能拿下整台机器，
而那一行在 diff 里毫不起眼。

### 人在中间那一关

`deploy` job 绑定在 `production` 环境上。到 Settings → Environments →
production 给它配 **required reviewers**，每次部署就都要人点一下同意。

这一关值得留着：发错一篇文章，点一下撤下就行；发错一个二进制，站点就
下线了。两者的撤销成本差了两个数量级。

### 回滚只回滚二进制，不回滚数据库

`deploy.sh` 在健康检查失败时把上一个版本换回去。它**不动数据库**。

这一条目前成立，是因为所有迁移都是加列和加索引，而查询用的是显式列清单
（`postCols`），多出来的列会被忽略——旧二进制能在新库上正常跑。

哪天有了破坏性迁移（改列、删列、改语义），这个假设就不成立了。写那条
迁移之前必须先想清楚回滚路径，而不是等回滚失败时才发现。

### 不用 systemd 也能用

`deploy.sh` 的重启命令是 `CLIGC_RESTART` 环境变量，默认
`systemctl restart cligc`。用 OpenRC、supervisord 或 docker 的换掉即可，
脚本本身不假设你用 systemd。

## 明确不做的

- **开放注册。** 这是定位，不是待办。整套设计建立在"作者可信、读者不可信"
  这个前提上：发布不限速（只有针对 AI 的每日上限）、后台不做租户隔离、
  作者能改站点设置。加一个注册入口不是加一个页面，是把上面每一条都推翻重来。
  想做多人 UGC 站，fork 之后从权限模型开始改，不要在这套假设上叠。

- **富文本评论。** 评论永远是纯文本、不生成可点击链接。这个站的整个论点
  就是"别变成外链农场的宿主"。

- **验证码。** 三道闸门挡的是自动化脚本；真人手工刷仍然能进队列，只是被限死在
  3 条 / 10 分钟 / 每个 /64。要挡真人得上验证码，而那会牺牲掉所有正常读者的
  留言意愿——以这个站的评论量不划算。

## 还没做的

- **评论通知。** 有新的待审评论时没有任何提醒，只能靠后台页签上的红点。
- **草稿版本历史。** 现在保存就是覆盖，改错了只能靠浏览器本地那份暂存找回。
- **标签合并。** 打重了的标签（Go / golang）只能一篇篇改。
- 前端目前是标准表单 POST + 一小段原生 JS（渐进增强，关掉 JS 也能用）。
  想换 htmx 的话，表单结构已经兼容，加上 `hx-post` 属性并引一个
  vendor 文件即可。
